# CherrySecurity M1 verification results

Last updated 2026-10-18. This report distinguishes source checks already observed from deployment and endpoint checks that require separate approval. It is not a security certification.

| Check | Observed result |
| --- | --- |
| Agent module integrity | `go mod verify` passed with the project-local Go 1.27.2 toolchain |
| Windows agent tests | `go test ./... -count=1` passed, including policy, timeline, bounded durable queue, delivery trust, current-user DPAPI, current-user pipe authentication, collectors, helper-loss gaps, configuration, ACL construction, and installer planning |
| Static checks | `go vet ./...` and `git diff --check` passed |
| Go vulnerability scan | Official `govulncheck@v1.9.0 ./...` completed on 2026-10-18 and reported no reachable vulnerabilities |
| Linux portability | The platform-neutral `internal/agent` package passed `go vet` and the race detector in a `golang:1.27.2-bookworm` container with no network and read-only source |
| Windows artifacts | The installed build is `artifacts\agent\batch-c6` from commit `fec4c6e` (service `2489a03a…`, helper `2a8239b8…`, control `d5632818…`, full hashes in its `SHA256SUMS`); Authenticode reports all three as `NotSigned`, as expected for local development |
| In-place upgrade | `--action upgrade` moved the installed agent from `batch-c5` to `batch-c6` and printed the old and new hash of each binary. Afterwards the same device (`2846eac0…`) kept reporting with no new key used, one active device, `helper=healthy`, 0 lost events and events still arriving (500 → 620), and no `.new`/`.old` files were left. Because the upgrade restarted the service, this also showed the LocalService process reading its DPAPI-protected credential after a restart |
| Windows install and enrollment (Batch C) | On the owner's Windows 11 Pro 26100 PC for user `husain\husai`: the elevated install created the service (LocalService, delayed auto start, crash-only restarts at 10/30/60 s, unrestricted service SID), the helper task (selected user, interactive only, least privilege), protected install and data folders, and a service ACL that lets authenticated users only query status. Enrollment by an elevated administrator succeeded and the key shows as used. Observed: the service stays running, a non-admin stop is refused (access denied), the standard user cannot read `C:\ProgramData\CherrySecurity`, the helper connects (`helper=healthy`), heartbeats and policy refreshes return 200 through the ingress, 500 Windows-service events uploaded with 0 lost, and the agent correctly reported `outside_schedule` at 21:24 Asia/Kolkata. The owner reported the agent working |
| Backend native contract | Full backend suite passed with the race detector against a throwaway PostgreSQL 17 as the restricted cherryapp role (19 tests, including the two-tenant isolation matrix and row-level security without tenant filters); go vet and gofmt clean |
| Console | 18 frontend unit tests, TypeScript check and production build passed; the owner confirmed sign-in, Overview, audit log and one-step tenant creation on Kali; all 4 Playwright browser tests passed on this build (Edge, Kali's isolated `browser-test` profile and `cherrysecurity_test` database at schema 4): owner provisioning, one-time key display, enrollment and replay, the administrator's Overview, devices, services and report totals, mobile-width overflow, device revocation, invalid sign-in, the key-issuance race, and sequence-gap coverage |
| Kali deployment | main deployed 2026-10-18: schema 2 → 4 in one migration transaction after a verified backup; readiness 200 through nginx and the SSH tunnel |
| Agent TLS ingress | Live on `192.168.193.129:8443` with a private ECDSA P-256 CA and an IP-only 30-day server certificate (expires 2026-11-17); from Kali, a Go client on Windows and Windows `curl.exe`: 401 without a device token, 404 for other routes, 405 for wrong methods, TLS 1.3, untrusted CAs rejected; no firewall change |
| Scope validation | Acceptance and measurement scripts validate fixed CherrySecurity service/task/directory names, absolute paths, three expected binary names, and lowercase SHA-256 values before any mutating mode |

Generated binaries are ignored by Git. Their current hashes are recorded in `D:\Cherry-security\artifacts\agent\SHA256SUMS`; rebuilds intentionally change that local manifest. They are unsuitable for customer deployment until code signing and release verification are designed and approved.

Batch B is complete: the database backup, migrations 003 and 004, private TLS material, and the agent ingress on the verified NAT address are in place, and no firewall change was needed. The server certificate must be renewed before 2026-11-17. Batch C is complete for installation and enrollment. Four defects that only a real install could expose were found and fixed in turn: the installer discarded `schtasks`/PowerShell output (`de4b0f3`), the helper task XML was UTF-8 where `schtasks` requires UTF-16 (`e3fc0dc`), the enrollment pipe's ACL omitted the service's own SID so the service stopped before enrollment (`90d0675`), and the helper could not verify the service because standard users cannot open a LocalService process (`5e5c246`). Not yet observed: application activity inside the collection schedule, another Windows user being denied, and the tray notice text. The two uninstall defects found during Batch C (a still-locked helper executable, and the control program unable to delete itself) are fixed in `fec4c6e`, which also added the in-place upgrade; the uninstall fixes are covered by unit tests but have not yet been run against the installed agent. Batch D is pending: foreground/idle/lock/suspend/service observations, helper termination, crash and administrator-stop behavior, bounded outage/retry, revocation, and the real eight-hour CPU/RAM/disk measurement.

Current known limits: no browser-domain collection (M2), no concurrent-session support, no production signing, no upgrade path for the endpoint or CA, and no real endpoint performance evidence. A first private-bytes reading on the installed agent was about 54 MiB for the service and 52 MiB for the helper, above the 50 MiB combined pilot target; that is one sample, and the eight-hour Batch D measurement is still required. Host-wide network adapter totals in the measurement script are context only and cannot be attributed solely to CherrySecurity; CPU, private bytes, process I/O, and CherrySecurity data size are process/scoped measurements.

Implementation decisions and exact limitations are in [the M1 ledger](M1-LEDGER.md). Build, installation, enrollment, status, and removal behavior are in [the M1 Windows operations guide](../M1-WINDOWS-OPERATIONS.md).
