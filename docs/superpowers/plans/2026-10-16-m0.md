# CherrySecurity M0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for inline implementation, or superpowers:subagent-driven-development if the user selects delegated execution. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run CherrySecurity Console, Go API, PostgreSQL, and simulated endpoint telemetry in Kali, demonstrating organization/key provisioning, isolation, accurate reports, and persistence.

**Architecture:** Keep editable source in the Windows workspace and deploy a synchronized source copy to Kali over authenticated SSH. Run the entire application stack in Docker Compose inside Kali. Serve the built React app and proxy `/api` through one web container; PostgreSQL and API remain internal to the Compose network. Initially access the console through SSH port forwarding, avoiding public VM ports and certificate bypasses.

**Tech Stack:** Go standard HTTP library; PostgreSQL with pgx; versioned SQL migrations; React, TypeScript, Vite; Docker Compose. Resolve current supported stable runtime versions and lock dependencies during implementation. Use Go's maintained password-hashing library rather than implementing cryptography.

**Spec:** `docs/PRD.md`, version 0.3. This plan implements M0 only. Windows collectors, extensions, installers, performance claims, and commercial rollout remain in later milestones.

## Global Constraints

- The product and brand name is CherrySecurity.
- Go for the backend and endpoint agent.
- React for the administrator frontend.
- The Kali VM hosts the complete backend, database, and dashboard server stack for local testing.
- The Product Owner creates organizations and allocates endpoint enrollment keys to each organization.
- For the initial version, one key enrolls one endpoint.
- Reveal each key secret once at issuance for controlled handoff to the organization administrator; store only a verification hash and never include the secret in logs or audit records.
- The Product Owner has platform provisioning authority; this does not automatically grant access to employee activity.
- Use simulated telemetry only in M0; visibly identify it in the console.
- Never commit credentials, generated enrollment secrets, private keys, database files, or backups.
- No changes to VMware networking, VM resources, or existing guest data without a concrete need. Do not reset the VM or delete volumes.

## Review Focus

- Concurrent enrollment: exactly one redemption succeeds for a single-use key; no orphan device or credential is created (Task 3).
- Authorization through guessed identifiers: organization users cannot read other customers' records, and the Product Owner cannot read employee activity (Tasks 2–5).
- Offline retries and conflicting event IDs: identical retries do not change reports; conflicting payloads fail visibly without partial writes (Task 4).
- Reporting across local midnight or an offset change: intervals split by the configured reporting timezone, with browser time kept separate from application totals (Task 5).
- Restarts, expired/revoked sessions, and restored databases: persistence and isolation survive restart/restore, while revoked credentials remain rejected (Tasks 2, 4, 8).

## Task 2 — Persistent schema, authentication, and role boundaries

**Files:** migration/bootstrap commands, initial SQL migration, `backend/internal/httpapi/auth.go`, `backend/internal/store/accounts.go`, `backend/tests/auth_test.go`, `docs/api-m0.md`.

**Interfaces:** `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`; server-side random sessions with hashed tokens and HttpOnly SameSite cookies. Mutating console APIs require a matching CSRF token and same-origin validation. Roles: `product_owner`, `org_admin`, `org_viewer`.

- [ ] Write integration tests for invalid login, session expiry/logout, unauthenticated requests, CSRF rejection, role escalation, and organization-bound account queries. Verify failure.
- [ ] Implement schema migrations under a migration lock; refuse startup with an incompatible schema. Bootstrap the first Product Owner interactively with a hidden password prompt, never a checked-in default password.
- [ ] Implement securely hashed passwords, random revocable eight-hour sessions, bounded login throttling, generic credential errors, and explicit role checks. Use secure cookies when serving HTTPS; document the loopback-only HTTP development exception through SSH.
- [ ] Run auth integration tests against a dedicated disposable test database, never the development database. Check that logs contain neither passwords nor session tokens; commit.

## Task 3 — Product Owner provisioning and single-use enrollment

**Files:** `backend/internal/httpapi/provisioning.go`, `backend/internal/store/provisioning.go`, `backend/tests/enrollment_test.go`, `docs/api-m0.md`.

**Interfaces:** Owner routes: `POST /api/owner/organizations`, `POST /api/owner/organizations/{id}/admins`, `POST /api/owner/organizations/{id}/keys`, `GET /api/owner/organizations/{id}/keys`, `POST /api/owner/keys/{id}/revoke`. Organization route: `GET /api/org/keys` (metadata only). Endpoint route: `POST /api/agent/enroll` with `{enrollment_key, hostname, os, agent_version, simulated}` returns `{device_id, device_token}` once.

- [ ] Write tests proving admin/viewer cannot provision organizations or keys; expired/revoked/used keys fail; cross-organization key metadata is inaccessible; simultaneous redemption yields one successful device. Verify failure.
- [ ] Implement creation and initial-admin provisioning, random 256-bit enrollment secrets with hashes, default 24-hour key expiry, allocation count 1–100 per request, issuance metadata and revocation. Return secret values only in issuance responses with `Cache-Control: no-store`.
- [ ] Atomically consume a key and create its organization-bound device and hashed device credential in one transaction. Reject caller-supplied organization routing. A lost successful enrollment response requires owner replacement-key issuance; document this M0 recovery limitation.
- [ ] Add metadata-only audit records for provisioning/key lifecycle actions. Confirm secrets never appear in list endpoints or audit logs.
- [ ] Run the full provisioning/enrollment test suite and commit.

## Task 4 — Durable, scoped telemetry ingestion

**Files:** `backend/internal/httpapi/ingestion.go`, `backend/internal/store/ingestion.go`, `backend/internal/telemetry/events.go`, `backend/tests/ingestion_test.go`.

**Interfaces:** Device bearer authentication for `POST /api/agent/heartbeat` and `POST /api/agent/events`. Batch envelope: `{schema_version:1, events:[...]}`; event fields: `event_id`, `session_id`, `sequence`, `observed_at`, `kind`, and strict kind-specific payload. Activity uses UTC start/end intervals; browser payload accepts a hostname only; service payload includes identity, state, startup type. Response acknowledges committed event IDs only. `POST /api/org/devices/{id}/revoke` revokes an organization-owned device.

- [ ] Write tests for duplicate retries, conflicting duplicate IDs, cross-device IDs, revoked credentials, malformed/oversized payloads, non-hostname browser values, and rollback on any invalid record. Verify failure.
- [ ] Implement a 1 MiB uncompressed request limit, at most 500 records per batch, unknown-field rejection, and a database uniqueness constraint on device/event ID. Reject different content for an existing ID with 409 and roll back the batch.
- [ ] Preserve observed and received timestamps separately. Accept observations within the organization's raw-retention window and at most five minutes into the future; return explicit validation errors otherwise. Reject overlapping application intervals for a session; browser intervals are a separate subset, never additive work time.
- [ ] Update heartbeat/current collector state without appending unlimited history. Keep newer service observations when older batches arrive; record sequence gaps as coverage information.
- [ ] Run ingestion, revocation, transaction, and duplicate tests against PostgreSQL; commit.

## Task 5 — Organization reports and deterministic simulator

**Files:** `backend/cmd/simulator/main.go`, `backend/internal/httpapi/reports.go`, `backend/internal/store/reports.go`, `backend/internal/telemetry/reports.go`, report tests and fixture data.

**Interfaces:** Organization-scoped `GET /api/org/devices`, `GET /api/org/devices/{id}`, `GET /api/org/devices/{id}/services`, `GET /api/org/reports/daily?date=YYYY-MM-DD&device_id=...`. Return timezone, observation coverage, simulated label, foreground/idle durations, application breakdown, and separate hostname breakdown. Missing data is unknown, never zero activity.

- [ ] Write report tests using exact expected durations, including a 600-second application interval containing 300 seconds of browser activity: total application activity stays 600 seconds. Include timezone-midnight and daylight-saving boundaries, guessed IDs, owner denial, and stale/offline heartbeat transitions.
- [ ] Implement range validation, interval splitting by reporting day, scoped queries, service state reads, and separate coverage/connectivity fields. Add materialized daily summary storage and idempotent updates so later raw cleanup preserves summaries for their own retention period.
- [ ] Implement a fixture-only simulator that prompts for an enrollment key without echo, saves device credentials with restrictive permissions, persists its event IDs, and supports replay without re-enrollment. All fixture devices are flagged simulated. It performs no real application/browser/service collection.
- [ ] Create deterministic data for two organizations and compare API output to expected fixture totals before and after replay. Test raw cleanup after seven days and summary cleanup after 30 days using an injected clock; implement the scheduled cleanup in the API process.
- [ ] Run backend tests and Go static checks; commit.

## Task 6 — CherrySecurity Console workflows

**Files:** `web/src/` application entry, API client, login, owner provisioning/key pages, organization device/report pages, frontend unit tests and browser acceptance tests; `web/package.json` and lockfile.

**Interfaces:** Consume the documented same-origin `/api` contracts only. Owner pages never fetch employee activity. Organization pages never expose owner provisioning actions.

- [ ] Write failing tests for role-based navigation, key secret reveal-once behavior, inaccessible detail IDs, login expiry, unavailable API, and simulated/coverage labels.
- [ ] Implement accessible React forms and tables with CherrySecurity branding, explicit errors/loading/empty states, organization timezone, last update, device/service detail, and report filters. Avoid storing session credentials or key secrets in browser persistent storage.
- [ ] Refresh visible reports every 30 seconds and cancel polling when the view is unmounted. Make device revocation and unused-key revocation explicit user actions.
- [ ] Run type checks, frontend tests, production build, and role-based browser checks. Check mobile-width navigation and keyboard form use; commit.

## Task 7 — Backup and isolated restore

**Files:** `scripts/backup.sh`, `scripts/restore.sh`, `README.md`, database restore acceptance checks.

**Interfaces:** Backup writes a restrictive-permission timestamped `pg_dump` custom-format file outside tracked source. Restore requires an explicitly named empty target database and refuses the active development database.

- [ ] Create a fixture backup, then demonstrate the initial restore check fails before restore implementation.
- [ ] Implement scripts that preserve command exit status and never automatically drop databases or remove volumes. Document that backup files include sensitive records and require controlled storage.
- [ ] Restore into a separate database; verify organizations, enrollment lifecycle, device revocation, audit records, event counts, report totals, and repeat-upload behavior. Remove only the explicitly created disposable test database after validation.
- [ ] Document actual backup/restore commands and results; commit.
